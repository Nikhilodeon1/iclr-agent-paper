# Run guide: Wave 1 on one pod

Pod facts this assumes: 5 GB persistent home (code and CSVs only), large `/tmp` scratch that is
wiped on restart or crash (the Python environment lives there), GPU pod such as an A40
(12 vCPU, 32 GB) or V100 (16 cores, 64 GB). **No datasets are needed for Wave 1.** Everything
is generated by the script. Real limits are read from the container, not `free -h`.

## 0. On your machine (once)
```
git add -A && git commit -m "pod scripts, jobs, analysis" && git push
```
Do this **before** starting the pod; a missing file on the pod almost always means it was not pushed.

## 1. On the pod (first time, and again after any crash or restart)
```
git clone <your-repo-url> project && cd project
bash pod/setup_env.sh            # builds the environment in /tmp, then runs the preflight
```
It must end with `PREFLIGHT OK`. If it says the torch build has no `sm_70` kernels (V100):
```
TORCH_INDEX=https://download.pytorch.org/whl/cu118 bash pod/setup_env.sh
```
Every new shell: `cd project && . pod/env.sh && python pod/preflight.py`

## 2. Launch
```
bash pod/launch.sh wave1         # starts H, A, B, E: four background processes, one per job
```
It refuses to start a job whose CSV already exists, so nothing is overwritten or doubled.
One job alone: `bash pod/launch.sh H`. The jobs keep running if you close the terminal.

**Check the GPU is actually used.** First line of each log must be `device=cuda`:
`head -1 /tmp/project_scratch/logs/H.log`. `launch.sh` now runs the preflight first and refuses to start on a
machine without a working GPU, and the script itself exits with `REFUSING to run on CPU` if CUDA is missing.


## Wave 2 (run this next)

```
git pull                                   # REQUIRED: new experiment modes
bash pod/launch.sh wave2                   # M1 M2 M3 M4 M5 K1 K2  (7 jobs)
python pod/status.py
```
Then, when those finish: `bash pod/launch.sh wave3`  (I C D B2 — 4 jobs).

Expected rows: M1-M5 48 each, K1 168, K2 112, I 96, C 120, D 84, B2 360.
M4 and M5 train a 25M-parameter model and are the slowest; everything else is the
0.8M model you have already run. If seven at once is too many for the card, start
M1 M2 M3 K1 first and the rest when they finish.

**One thing to check before leaving it:** M4's log should print `params=25,302,081` and a
`clean_loss` similar to M1's. If `clean_loss` at 512:8 is much worse than at 64:2, the big
model is badly tuned at lr 1e-3 and the comparison is confounded — tell me and I'll adjust
before you spend more time. (M5 is the control for exactly this.)


## Wave 4 (Jobs F and G)

```
cd ~/iclr-agent-paper && git pull && . pod/env.sh
bash pod/add_hf.sh                  # installs transformers + datasets into the EXISTING env (Job G only)
bash pod/launch.sh wave4            # F1 F2 F3 F4  (32 rows each)
bash pod/launch.sh GS               # 2-row Pythia smoke test, a few minutes
python pod/status.py
```
**Check the smoke test before starting G:** `cat experiments/poisoning/results_smoke_rt.csv` must show 2 rows with a finite
`clean_loss`, and a higher `asr` at `n_poison` 256 than at 16. If it errors, paste the traceback and do not start G.
```
bash pod/launch.sh G                # 100 rows; not resumable, so do not kill it
```
Time G from the smoke test: it ran 400 steps, so G's rate is `400 / GS elapsed seconds`, and G is 60,000 steps.

Send back: `results_ds_sgd_n64.csv`, `results_ds_sgd_n128.csv`, `results_ds_wd0.csv`, `results_ds_ctrl.csv`, `results_realtext_5seed.csv`.
Run `bash pod/pack_results.sh` for all of them. A `DONE` after about a second means every cell was already present, not that it ran.

## 3. Check progress
```
python pod/status.py             # state, rows done/expected, errors, ETA, last log line, GPU, RAM
tail -f /tmp/project_scratch/logs/A.log      # live log for job A (Ctrl-C leaves the job running)
nvidia-smi                       # GPU use and memory
```
**Concurrency check, 5 minutes after launch:** Job H runs alone in about 0.6 h. If its ETA in
`status.py` is above about 1 h, four processes are slowing each other: stop the last two
(`kill $(cat /tmp/project_scratch/logs/E.pid)`; same for B), let H and A finish, then launch them.

## 4. Done?
`status.py` shows `DONE` with rows equal to expected (H 80, A 90, B 120, E 120).
`STOPPED` with fewer rows means it died: do **not** relaunch. Rows already written are kept.
Send me the log tail that `status.py` printed and the CSV.

## 5. Get results back
```
bash pod/pack_results.sh         # makes ~/results_wave.tgz with the CSVs only
```
Download it from the pod's file browser, unpack on your machine, and **upload the CSVs into this
chat**. The pod has no credentials for your repository, by design. Then:
`python experiments/poisoning/analyse_jobs.py results_<name>.csv`, or just send them to me.

## When something goes wrong
- `CUDA`/driver error at preflight: pick another pod or the cu118 line above. Do not start jobs.
- `ERROR` lines in a log: one cell failed and the job continues; send me the first few.
- Pod restarted: environment is gone (scratch), repo and CSVs on home survive. Rerun step 1,
  check `status.py`, and send me the partial CSVs.
- Never run the same job twice into one CSV.
